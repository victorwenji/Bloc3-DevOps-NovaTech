Date 24 juillet 2026
Item Rédaction du plan de tests
Référence Audit J1
01

Objectif du plan

Documenter la stratégie de test avant de l'implémenter : quels niveaux couvrir, quels scénarios sont critiques, avec quels outils et quel seuil de sortie.

L'état réel de l'exécution — nombre de tests, couverture effective et résultats — est reporté dans docs/RAPPORT-ETAT-CORRECTIONS.md.

Une seule source de vérité Ce document définit la stratégie. Les résultats d'exécution restent dans le rapport d'état des corrections afin d'éviter les divergences.
02

Pyramide de tests retenue

Trois niveaux complémentaires : rapides et isolés à la base, puis progressivement plus proches du comportement réel de l'application.

E2E — Playwright 5 parcours clés · stack réelle
↓
Intégration — Jest + Supertest HTTP réel · DB mockée · JWT réels
↓
Unitaire — Jest Logique métier et middlewares
U
Tests unitaires

Fonctions pures : cotisations, heures supplémentaires, solde de congés et middlewares requireAuth / requireAdmin.

I
Tests d'intégration

Routes Express réelles via Supertest, PostgreSQL mocké et JWT réels. Vérification du contrat HTTP et des requêtes SQL.

E
Tests E2E

Stack réelle via Docker Compose : gateway, services, PostgreSQL et frontend. Validation des parcours utilisateurs complets.

03

Flux de validation

Les différents niveaux s'empilent pour détecter rapidement les régressions tout en conservant une validation proche des conditions réelles d'utilisation.

Code Push / Pull Request
→

→

04

Scénarios critiques

Les scénarios suivants constituent la couverture minimale attendue pour les fonctions sensibles du système HRFlow.

# Scénario Niveau Pourquoi c'est critique
1 Login valide → JWT signé avec le bon rôle Intégration Racine de l'authentification. Une régression bloque l'accès ou peut provoquer une usurpation de rôle.
2 Login invalide → 401 sans fuite d'information Intégration Empêche l'énumération des comptes et les réponses révélant l'existence d'un utilisateur.
3 Injection SQL sur l'email de login Intégration Critique Régression de la correction Phase 1 : la requête doit rester paramétrée.
4 /paie/migrate et /conges/debug/all sans token ou non-admin Intégration P1 Protection obligatoire issue de l'incident du 14/15 août 2024.
5 Calcul du solde de congés Unitaire Intégration Donnée directement visible par les salariés. Une erreur impacte la confiance dans l'application.
6 Majoration des heures supplémentaires de 25 % Unitaire Correction métier directement liée à la paie versée.
7 Échec Stripe lors du calcul de paie Intégration Le comportement actuel doit rester documenté et testé pour éviter une régression silencieuse.
8 Route protégée du gateway sans token → 401 Intégration E2E Défense en profondeur du système d'authentification.
9 Login UI → dashboard + solde affiché E2E Parcours utilisateur principal. Permet de détecter les problèmes de proxy et d'URL.
10 Login échoué → message d'erreur E2E Empêche les échecs silencieux côté interface.
11 Accès direct à /dashboard sans session E2E Vérifie qu'aucune donnée protégée n'est accessible sans authentification.
12 Recrutement : candidature → consultation E2E API Module historiquement non couvert. Inclut la problématique sensible de l'upload CV.
13 Congés : demande authentifiée + calcul des jours E2E API Traverse le gateway, le service et une vraie base PostgreSQL.
05

Outils retenus

Les outils sont choisis pour rester cohérents avec l'écosystème Node/React existant et limiter la complexité de la CI.

J

Jest

Runner unitaire et intégration pour les services backend et le frontend. Déjà présent dans le projet.

S

Supertest

Requêtes HTTP contre l'application Express exportée, sans ouvrir de véritable port.

R

Testing Library

Tests React orientés comportement utilisateur : rendu, interactions et erreurs.

P

Playwright

E2E navigateur et API contre la stack Docker réelle. Permet de couvrir les parcours utilisateur complets.

T

Trivy

Scan de vulnérabilités des images Docker dans le stage Sécurité du pipeline.

Z

OWASP ZAP

Scan dynamique baseline de l'API exposée pour compléter les contrôles statiques et les scans d'images.

08

Hors périmètre

Certaines catégories de tests sont volontairement exclues de cette campagne afin de conserver un périmètre réaliste.

—
Tests de charge / performance
Non demandés dans le périmètre actuel.
—
Tests de migration de schéma
Aucune migration versionnée n'existe actuellement dans le repository.
—
Coverage frontend exhaustif
Seuls Login et Dashboard sont actuellement concernés ; le plan ne cherche pas à couvrir chaque composant.
09

Principe directeur

Tester rapidement en bas de la pyramide, tester réellement en haut, et empêcher toute régression critique d'atteindre le déploiement.

Le plan privilégie une couverture progressive : logique métier avec Jest, contrats HTTP avec Supertest, puis validation des parcours réels avec Playwright. Les contrôles de sécurité complètent cette stratégie avant le staging et la production.
